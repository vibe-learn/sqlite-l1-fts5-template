        # sqlite — Полнотекстовый поиск: FTS5

        Homework-шаблон для урока **l1_fts5** (Полнотекстовый поиск: FTS5) на платформе Vibe Learn.

        ## Что делать

        На Python (stdlib sqlite3) реализуй мини-поисковик по статьям. Функции: index_article(conn, title, body),
search(conn, query, limit) → список (title, score), отсортированный по релевантности. Под капотом —
FTS5 virtual table (проверь доступность FTS5 через `pragma compile_options` или try/except на CREATE).
search использует MATCH + ORDER BY rank (bm25). Сравни в отдельной функции время и качество с
наивным LIKE-поиском на том же корпусе. Тесты гоняют на :memory:-базе: проверяют, что (1) поиск
находит документ по термину, (2) результаты отсортированы по bm25 (более релевантный выше), (3)
запрос-фраза в кавычках работает. Если FTS5 в сборке недоступен — тест пропускается с понятным
сообщением.

## Контекст (из transfer-задачи урока)

У тебя приложение-читалка статей на SQLite: таблица articles(id, title, body, author, published_at),
~200k статей. Сейчас поиск сделан как `WHERE body LIKE '%' || :q || '%' OR title LIKE '%' || :q || '%'`.
Пользователи жалуются: поиск медленный (секунды), не находит словоформы (ищут «бежал» — не
находят «бежать»), и результаты в случайном порядке. Менеджер предлагает «поставить
Elasticsearch».

**Вопрос:** объясни:
(a) почему текущий LIKE-поиск медленный и почему индекс по body не спасает;
(b) как переписать на FTS5 (таблица, MATCH, ранжирование) и стоит ли делать external-content;
(c) какой токенизатор выбрать с учётом словоформ и почему;
(d) честно: оправдан ли тут Elasticsearch, или FTS5 закрывает задачу — и при каком росте
    требований Elasticsearch всё-таки понадобится.

## Recap из урока

- FTS5 — встроенный **полнотекстовый поиск** в SQLite: `CREATE VIRTUAL TABLE docs USING fts5(...)`, поиск через `MATCH`. «Поиск в коробке» без Elasticsearch.
- `LIKE '%term%'` — это **O(N) скан** без индекса, ранга и словоформ. FTS5 — инвертированный индекс (термин→документы) + ранжирование bm25 + токенизация.
- Ранжирование: `ORDER BY rank` по `bm25()` (**меньше = релевантнее**). Колонки можно взвешивать: `bm25(docs, 10.0, 1.0)`.
- Токенизаторы: **unicode61** (дефолт), **porter** (стемминг EN), **trigram** (подстрока + опечатки).
- **External-content** хранит только индекс, ссылаясь на исходную таблицу (экономит место), но требует **триггеров** для синхронизации. FTS5 НЕ нужен для точного равенства/префикса (там B-tree) и для распределённого кластерного поиска (там Elasticsearch).

        ## Как работать

        1. Платформа Vibe Learn создаёт копию этого репо в твоём GitHub-аккаунте по клику «Начать домашку» на странице урока (через GitHub `/generate`, codecrafters-pattern).
        2. Склонируй копию локально, реализуй TODO в `main.py`, прогони тесты, запушь.
        3. CI (`.github/workflows/ci.yml`) ставит зависимости и запускает `pytest` на каждый push. Платформа слушает результат через webhook от GitHub Actions и обновляет статус домашки на странице урока.

        ## Локальное окружение

        - Python 3.12+
        - SQLite встроена — **никакого сервера и docker-compose**. БД это один файл (`DATABASE_PATH`) или `:memory:` в тестах. Модуль `sqlite3` входит в stdlib, ставить драйвер не нужно — единственная зависимость это `pytest`.

        ## Запуск

        ```bash
        # Установить зависимости (только pytest)
        pip install -r requirements.txt

        # Прогнать тесты (бегут на :memory:-базе, ничего поднимать не нужно)
        pytest

        # Запустить main (печатает marker; замени stub на реализацию)
        python main.py

        # На файловой БД (нужно для backup/vacuum-уроков):
        DATABASE_PATH=./app.db python main.py
        ```
